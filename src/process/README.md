# 컨트롤 파트 설계

컨트롤 파트는 인식 단계에서 받아 온 정보를 바탕으로 어떠한 동작을 수행할지 결정하고, 실제로 동작을 수행할 것이다.

## 설계 목표

컨트롤 파트를 설계할 때 하기 목표를 모두 달성하고자 한다.

1. 고속 동작 : 컨트롤 파트가 동작할 때 프로세스에 blocking operation으로 인한 유휴가 있어서는 안 된다. 특히 하드웨어 통신을 기다리는 비효율적인 작업을 해서는 안 된다.

2. 독립적 개발 : 컨트롤 파트는 전체적으로 여러 부분으로 나누어 개발될 것이다. 이 각 부분은 필요한 인식 파트가 모두 구현되었다는 조건 하에 다른 부분에 관계 없이 독립적으로 작동이 가능해야만 한다.

3. 개발의 편의성 :

   - 개발을 시작하기 위해 해야 하는 초기 설정을 최대한 줄인다.
   - 개발을 시작하기 위해 건드려야 하는 파일을 최대한 줄인다.
   - 이상적으로는 파일 하나를 새로 만들고 거기에 함수 하나만 작성하면 그것만으로도 동작하는 것이 목표다.
     - 예를 들어 각 state를 구현한 로직이 다른 파일에 있다고 가정하자. 그것만으로도 로직 파일을 하나 만들고, 그것의 헤더를 또 만들고, 메인 파일에서 로직 파일을 참조하도록 바꿔야 하므로 파일을 세 개 건드려야 한다.

- 이는 근본적으로 기능 추가나 삭제를 용이하게 하기 위함이다.

4. 개발의 보편성 : 일반적으로 자주 사용되는 방법을 사용하여 개발이 가능해야 한다. 복잡한 전처리기나 쉘 스크립트를 이용한 트릭 등은 최대한 줄인다.

5. Stateless : 목표 2를 달성하기 위하여, side-effect를 없애기 위해 최대한 stateless하게 구현하도록 한다.

## 개발 상세

파일은 크게 다음과 같이 나누어진다.

- `control.c`
- `control.h`
- `mission-someMission.c`

### 용어 정의

#### mission

개발 시 state로 주로 언급했던, 완주를 위하여 해결해야 하는 각 과제를 말한다. state라는 용어가 혼란스러울 수 있으므로 mission이라는 용어를 대신 사용하기로 하자.

#### data

각 mission들이 공유할 수 있도록 해 주는 변수로, 전역 변수에 해당된다. 읽고 쓰기가 모두 가능하다. 각 state들에 파라매터로 이 변수의 포인터가 전달될 것이다. 굳이 전역 변수나 전역 structure를 만들지 않은 이유는 stateless하게 개발할 수 있도록 하기 위함이다.

### `control.c`

프로세스의 `main`함수가 포함된 파일이다. main함수가 실행되면 각종 초기화를 진행한다. 이후 다음 루프를 무한히 반복한다.

1. 모든 미션 조건 검사를 수행한다.
2. 미션 priority에 따라 수행할 미션을 결정하고, 해당 미션을 수행한다.

### `control.h`

Mission,Data 등 각종 struct에 대한 정보 및 weak function에 대한 정보를 담고 있다.

### `mission-someMission.c`

각 미션을 구현한 파일로, weak function을 override하여 실제로 구현한다.

## 논의

- state를 자동으로 추가하는 가장 효율적인 방법이 무엇일까?
- 자신이 담당한 state이외의 state를 모르고서도 개발이 가능한 것을 목표로 한다.
  - 가만히 생각해보니 이것이 가능했다면 바람직하지만, 불가능하다. 그럴 경우 다른 state를 모르는 것은 오히려 개발을 어렵게 만든다.
- 일단 조건 판단 state는 반드시 어떤 다른 state들이 있는지 알아야만 한다. 그렇다면 조건 판단 state를 여러 개로 분리하는 게 어떨까?
  - 이거 아주 좋은 아이디어인 것 같다.
  - 각 state파일과 메인 파일이 공유하는 것은 오직 조건 판단 함수이다.
  - 메인 파일에서는 조건 판단 함수를 실행하고, 최종적으로 가장 periorty가 높은 state로 진입한다.
- 그렇다면 알고리즘은 이것으로 결정.
- 다음으로, 파일을 작성하는 것만으로 state가 추가되고, main파일을 건드리지 않을 방법이 있는가?

  - 불가능하다면 왜 불가능한가?
  - 일단 런타임에서는 불가능함을 알 수 있다.
  - 현재까지로서는 weak 키워드를 사용하는 것 이상의 방법은 없어보인다.
  - 그리고 파일을 작성함에 따라 자동으로 추가되는것은 바람직한 방법이 아니다. 왜냐하면 충돌이 일어날 가능성이 존재하기 때문이다.

- stateless한 개발이 중요한가?

  - 인식 단계에서 입력을 받기 때문에 어차피 stateless하지 못하고 side-effect가 존재한다.
  - 만약 stateless하게 개발하지 않았을 경우, side-effect로 인해 발생할 수 있는 문제로는 어떤 것이 있는가?
  - side-effect라 함은, 동일한 입력이 주어졌음에도 hidden-variable로 인하여 다른 출력이 나오는 것이다.
  - state의 출력 상태를 결정할 수 있는 variable이 input으로 얻어지는 것 말고 어떤 게 있을까?
    - task 순서에 따른 이전에 수행된 task정도?
    - 전역 변수를 건드리는 것보다야 나을 것이다,

- 그렇다면 state 변수의 구조를 어떻게 결정할 것인가?
  - 일단 shared memory에 대한 접근이 여기서 가능해야 한다.
  - control board 호출은 자율에 맡기자.
  - 그리고 state별 strcuct가 따로 필요하다.
  - state가 반환해야 하는 / 설정해야 하는 값이 뭐가 있을까?
    - 자명히 priority가 있다.
    - 그리고 수행해야 할 함수정도...?
  - 출력은 판단 함수에서 반환하도록 하는 게 나을 수도 있다. 입력된 변수에 설정하는 것은 별로 좋지 않아보인다.
  - 특히 state variable에 출력 변수를 미리 만들어놓는 것은 기능 추가 / 제거 시에 해야 할 일을 늘린다.
  - 그러나 c++가 아니라 c로 개발할 경우 매번 malloc을 해야 한다.
  - 차라리 setPriority함수를 만드는 건 어떨까?
    - 함수 호출을 잊어먹을 수도 있다.
- 판단 함수는 반드시 미리 정의해줘야 한다. 그런데 실행할 함수까지 미리 정해주는 게 좋을까?
  - 단점 : 함수를 미리 설정해줘야 하므로 수정 / 추가에 많은 비용이 필요함, 사용자 단
  - 장점 : 함수를 반환하지 않고 priority만 반환해도 됨.
  - 단점이 장점보다 크므로 함수는 미리 설정하지 않기로 하자.
  - 만약 전처리기를 사용하여 설정을 한 번에 할 수 있다고 가정하면?
    - 그래도 각 Mission별로 필수 구현해야 하는 함수가 두 개가 되므로 좋지 않다.
- Mission struct와 판단 함수는 한 세트인데 이것을 매번 만들어야 한다. 생략할 수 있는 좋은 방법이 없을까?
  - 전처리기가 좋은 솔루션이 될 수 있다.
  - 어떻게 사용하면 좋을까?
  - C에서 lambda가 지원되면 좋았을 텐데.
  - struct에 배열로 집어넣는 것도 하나의 방법이다.
    - 해보니까 같은 타입들이 들어 있는 struct를 배열로 캐스팅할 수 있다.
    - 그러면 struct에 값을 쓰는 것으로 해도 무방하다.
- 그렇게 한다면 전처리기가 세 번 필요하다.
  - struct내에서 참조를 생성하기 위해
  - weak함수를 만들기 위해
  - weak함수를 실행하기 위해 main문 안에서.
  - struct와 weak함수는 링크되지 않음에 주의하라.

```c
typedef void (*MissionFunction)();

typedef struct{
  int missionPriority;
  int (*missionFunction)();
}Mission;

struct State{
  ShmData shm;
  // Some custom variables
  struct Missions{
    Mission missionA;
    Mission missionB;
    Mission missionC;
    // Mission ...;
    Mission missionZ;
  }
}
```
